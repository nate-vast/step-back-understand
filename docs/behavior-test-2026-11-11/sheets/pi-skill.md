1. Pi sends the model a request made of its short system prompt (with your global and project AGENTS.md appended), the declared tools, and the conversation so far, which comes from the session transcript that Pi records and can resume, fork or branch. The model's reply streams back; if it contains tool calls, Pi runs them and appends the results to the transcript. Another turn starts only because the model called tools: the loop keeps going until the model answers without calling any, and there is no maximum-step setting. I don't know the exact rules for messages you type while a turn is still running.

2. Codemode is a single tool that lets the model write a JavaScript script which calls Pi's other tools (including MCP tools) and non-chat models such as classifiers and image generators. The script runs in a QuickJS sandbox on the harness side, next to the agent loop, with no Node APIs, file system, network or timers; it can reach the outside world only through the `tools` and `models` objects, plus a small `store()`/`load()` for values kept across calls. When it finishes, only the script's output (what it returned or printed, capped at about 10,000 tokens by default) goes into the model's context, so intermediate tool results never do.

3. By default the server gets `codemode` exposure: its tools are not declared to the model and are not even listed in the codemode tool's description. Connecting the server switches the `codemode` tool on, and the model reaches the tools by writing a script that finds them with `searchTools()`, `describeTool()` or `ALL_TOOLS` and calls them. The other options are `deferred` (not declared up front, loaded on demand through a `tool_search` tool), `direct` (declared like a built-in tool and also callable from scripts) and `hidden` (registered but unreachable), and a `toolExposure` setting can override the mode per tool.

4. The original objection was context cost: MCP servers put every tool definition into the prompt (Zechner measured roughly 13.7k tokens for the Playwright server and 18k for Chrome DevTools), while a command-line tool with a README costs nothing until the agent needs it and composes through bash. Earendil's reasons for changing course were that MCP itself had changed over the year, that they would rather embrace the protocol and shape it than stand aside, and that the machinery it needs (a sandboxed interpreter) was also useful for other things such as calling the Jev classifier. It went into the core because an ordinary MCP extension, which already existed, lacked the metadata to decide whether a tool is visible to the model or only to Codemode, so tool loading itself had to learn about deferred and Codemode-only tools. They still say MCP is hard to compose.

5. Because those requirements would have bloated a coding agent whose whole point is to stay minimal. People wanted Pi outside the terminal, with very long conversations, reachable from several surfaces and steerable by several people, and that needs different machinery: a storage backend, every model and tool call as a checkpointed task that resumes after a crash, and one process owning the storage while clients attach. Earendil put that in a separate package that shares code and principles with Pi, and labelled it experimental with an API that may change, so the coding agent did not have to carry it.

6. Mario Zechner created Pi in 2025 as a reaction to Claude Code, which he felt had become a "spaceship" of features he did not need and whose changing prompt and tools kept breaking his workflows. The starting stance was minimalism and control over context: four tools (read, write, edit, bash), a system prompt and tool definitions under about 1,000 tokens, full access with no permission prompts, and deliberately no MCP, sub-agents, plan mode, to-dos or background bash. Pi became widely known because OpenClaw was built on it; after a flood of investor and company approaches, Zechner chose not to run a VC-funded startup and in April 2026 joined Earendil, co-founded by his long-time acquaintance Armin Ronacher, which took ownership of the project and trademark while he committed to the core staying MIT.

7. The headline reaction was big and mostly about the U-turn: the launch reached the top of Hacker News with roughly 1,700 points and 600 comments, and coverage led with a harness that had said no to MCP now shipping it. Specific criticisms were that Pi was "abandoning the minimality philosophy," that cache warming belongs in a plugin, that extension quality is uneven because it depends on each maintainer, and that the new fullscreen default was divisive (one user reported blinking under screen). The makers' answer on MCP was that it is off the model's context by default and reached through Codemode, so the original token objection still holds, and that they adopted it to influence it; for fullscreen there is a setting that restores the regular scrollback mode. I did not see replies from the maintainers in the discussion itself.

8. What I know is that Pi reads a project's `.pi/mcp.json` only after project trust has been granted, so with no saved trust decision that file should be skipped. I would expect the project's `.pi/extensions/` to be skipped on the same grounds, since they are code, and `AGENTS.md` to be loaded into the system prompt as plain instructions, but I don't know either of those for certain in 1.0, nor how a non-interactive run handles the missing trust decision. Either way the run is not safe: Pi has no permission system and its bash tool has full access, the repository's own files (AGENTS.md, code, test output) can steer the model, and fixing a failing test means executing the third party's code. I would run it in a throwaway container with no secrets or deploy credentials and restricted network, leave the project untrusted, and cut the run down to the tools it needs (the exact flags for disabling project extensions I'm not sure of).
