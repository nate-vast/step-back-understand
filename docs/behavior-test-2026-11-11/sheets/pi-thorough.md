1. Pi appends your message to the session, sends the conversation to the selected model along with the system prompt and tool declarations, and streams back the response; if the response contains tool calls, Pi runs them (without asking for approval) and records the results. The history for each request comes from the session transcript, which Pi stores as a tree in a JSONL file: it sends the current branch, with older messages replaced by a summary once compaction has run. Another turn starts when the model's response contained tool calls whose results need to go back to it, or when a steering message or queued follow-up is waiting; when the model answers with no tool calls and nothing is queued, the loop stops. I did not study the "How Pi works" page itself, so the exact wording of the stop condition is my reading of the usage and virtual-model docs.

2. Codemode is a built-in tool that lets the model write a JavaScript script which calls Pi's other tools (including MCP tools) and non-chat models such as classifiers and image generators, in any order and in parallel. The script runs on the harness side in a QuickJS sandbox (shipped as WASM) with no file system, network, Node APIs or timers, so it can only reach the outside world through `tools.<name>()` and `models`, and it can keep small JSON values across calls with `store()`/`load()`, which live in the session transcript. Only the script's output (what it returns, prints or emits with `text()`/`image()`, capped at 10,000 tokens by default) goes back into the model's context; intermediate tool results do not. The sandbox confines the script only: any tool it calls, such as `bash`, still has Pi's full permissions.

3. By default the server gets the `codemode` exposure: its tools are not declared to the model and are not even listed in the codemode tool's description, so they add no schema tokens, and the model reaches them by writing a Codemode script that finds them with `searchTools()`, `describeTool()` or `ALL_TOOLS` (Codemode turns on automatically once MCP is configured). The other options are `deferred` (tools stay undeclared until `tool_search` loads a match for the next model call), `direct` (declared to the model like built-in tools and also callable from scripts) and `hidden` (registered but unreachable). Exposure can be set per server and overridden per tool with `toolExposure`, including `*` patterns.

4. The original objection was context cost and poor composability: MCP servers dump thousands of tokens of tool descriptions into every session and route every result through the model, so Zechner preferred CLI tools with READMEs the agent reads on demand. The makers said two things changed: the MCP spec got a major update that made it "much less bad", and models are now trained to orchestrate tools through code (Codex relies on code mode for parallel tool calls), so with Codemode as the execution environment MCP becomes workable; their stated rule is to follow what the models are trained on. It went into the core instead of staying an extension because Pi's tool loadout had to change anyway for deferred loading, and marking tools as deferred or Codemode-only is something a normal MCP extension could not express well. They acknowledged it could have remained an extension, and a community adapter still works and replaces the built-in support if installed.

5. Because it is a different job with a different architecture, and folding it in would have made the coding agent bigger and more complex, which runs against Pi's minimalism. The coding agent is a single-user terminal tool handling one conversation in a local session file, while Durable is a library for applications reached from several surfaces: storage backends, a checkpoint before every step, many parallel conversations and forks, durable tasks and multiple clients steering at once. Keeping it as its own package (sharing pi-ai and the same principles) also lets its API keep changing while it is experimental, without destabilising a 1.0 coding agent. Earendil says explicitly that it is not a replacement for the coding agent.

6. Mario Zechner, an Austrian developer known for the libGDX game framework, created it; the repository dates from August 2025 and he published his design post in November 2025. The starting stance was "if I don't need it, it won't be built": four tools (read, write, edit, bash), a system prompt plus tool definitions under 1,000 tokens, no permission prompts ("YOLO" by default), and deliberately no MCP, sub-agents, plan mode, to-do lists, background bash or fullscreen TUI, with everything else left to extensions. Pi spread widely as the minimal agent inside OpenClaw, and in April 2026 Earendil (the public benefit corporation founded in 2025 by Armin Ronacher and Colin Daymond Hanna) acquired the project; Zechner joined as a major stakeholder and still leads its technical direction, the repo moved from his account to earendil-works, and the core stayed MIT licensed.

7. It was a big, mostly warm launch: the announcement went to the top of Hacker News with roughly 1,700 points and about 600 comments, and users praised the small prompt (especially for local models), vendor neutrality and hackability. Criticisms included that MCP, Codemode and a fullscreen default betray the minimalism people chose Pi for; that the bar for "proven" is uneven, since MCP waited nearly two years while support for the weeks-old Jev classifier arrived at once; doubt about the unverified "hundreds of thousands of weekly users" claim; and that a large Node.js/npm codebase is not really "minimal". Zechner answered the minimalism charge by pointing out that every addition is optional, that the only real added weight is a few megabytes of QuickJS WASM, and that the old scrollback mode is staying (`tuiMode: "regular"`); Ronacher answered the "proven" question by saying, in his words disappointingly, that they simply follow what the models are trained to do.

8. Print mode cannot show the trust prompt, and with the default `defaultProjectTrust` of `"ask"`, no override and no saved decision, Pi skips the protected project resources: `.pi/extensions/` is not loaded and `.pi/mcp.json` is not read (likewise project settings, skills, prompts, themes and system-prompt files). `AGENTS.md` is a context file, not a protected resource, so it loads regardless of trust and its instructions go into the prompt. That does not make the run safe: the repository's `AGENTS.md`, source files and test output can all steer the model, and Pi then runs `bash` and edits with the CI job's full permissions, with no sandbox and no per-call approval, so secrets and network access in the job are exposed. I would run it inside a container or VM with only the checkout mounted, no long-lived credentials (or scoped, short-lived ones) and restricted network, pass an explicit `--no-approve` so trust never depends on defaults, disable context-file loading for untrusted repos (the docs say this is possible; I do not remember the exact flag), and review the diff before using it.
